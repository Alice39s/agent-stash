# Skill Scout 架构与设计取舍

本文记录 `@agent-stash/dsh-skill-scout` 的数据流、关键决策和它们的依据。用户文档见 [README.md](README.md)。

## 目标

从已经结束的 Agent 会话里找出值得复用的程序性经验，以建议的形式交给用户审核。排序依次是：发现质量、可验证性、用户体验、运行成本、自动化程度、功能数量。

模型分两段参与：后台只请发现模型给一条线索写摘要，摘要里是一到几个 idea，每个 idea 说明发现了什么、Skill 做什么、打算新建或改进哪个 Skill；用户同意某个 idea 后，才请生成模型写这一个 Skill。摘要与草稿各是一次带完整证据包的请求，提示词评估里草稿的输出是摘要的 1.5 到 2 倍。被摘要判为不值得保存或被用户忽略的线索只花一次摘要请求，用户也能在模型写 Skill 之前否掉方向不对的 idea。

### 线索与 idea

一条线索是一组证据任务：规则检测出的 `repeated`、`recovery`、`complex`，或者用户发起的 `session`（整段会话）与 `selected`（搜索结果里勾选的任务）。线索的状态：

```mermaid
stateDiagram-v2
  [*] --> detected: 规则检测或用户提炼
  detected --> summarized: 摘要给出 idea
  detected --> skipped: 摘要判定不值得保存
  detected --> failed: 摘要超时、格式不符、证据不符
  failed --> detected: 摘要自动或手动重试
  skipped --> detected: 证据增加到两倍
  summarized --> detected: 重新摘要（idea 都还没有进展）
  detected --> dismissed: 忽略
  summarized --> dismissed: 忽略（没有已写入的 idea）
  skipped --> dismissed: 忽略
  dismissed --> detected: 恢复
```

摘要给出 idea 后，每个 idea 有自己的状态，和摘要里的下标对应：

```mermaid
stateDiagram-v2
  [*] --> proposed: 摘要给出
  [*] --> dismissed: 与被「忽略类似」的 idea 相近
  proposed --> ready: 用户同意，草稿通过校验
  proposed --> failed: 草稿失败（方案保留）
  failed --> ready: 用户重新生成草稿
  ready --> ready: 用户重新生成草稿
  ready --> written: 用户保存
  written --> ready: 撤销
  proposed --> dismissed: 忽略
  ready --> dismissed: 忽略
  dismissed --> proposed: 恢复（没有草稿）
  dismissed --> ready: 恢复（有草稿）
```

规则线索最多 3 个 idea，`session` 与 `selected` 最多 5 个。摘要提示词要求 idea 互不重叠、各自单独有用、Skill 名称不同，证据里只有一个就给一个；`checkSummary` 拒绝同一摘要里重复的 Skill 名称，任何一个 idea 不合格整份摘要不采用。线索合并沿用规则检测的指纹与相似度；idea 的去重分两处：不同线索里同名、还没结束的 idea 只显示最早的一张卡片，其余计入 `merged`；「忽略类似」记下 Skill 名称和标题词，之后摘要里同名或标题词 Jaccard 不低于 0.6 的 idea 直接记为已忽略。重新摘要会替换线索的全部 idea，所以只在没有 idea 生成过草稿、写入过或被「忽略类似」时允许。

存储里的状态不含进行中：摘要与草稿请求只记在 Host 内存里，视图据此显示 `summarizing` 与 `drafting`。插件重启时进行中的请求随 `AbortSignal` 取消，线索与 idea 停在请求之前的状态。每条线索的摘要、每个 idea 的草稿同一时间最多一个请求；后台摘要只处理规则线索，只在没有任何请求进行时发起，用户发起的请求不受这个限制。

## 决策

### 只认工具证据

`turn/end` 正常结束只说明 Agent 循环停了。Episode 的结果按工具结果计算：最后一次修改之后，每条命令的最后一次运行都成功才算成功，其中跑过测试、检查或构建的记为 `verified`。shell 的退出码从 DSH 追加的 `[exit code: N]` 读取，`run_code` 的子调用从 `tool/ptc-dispatch` 读取。Agent 的回复只作为证据包里的参考字段，提示词明确它不是成功的证明。用户下一条消息表示结果不对时，结果改为 `disputed`。

### 规则先行，模型只看候选

三类规则信号都只用 Episode 里的结构化字段，不调用模型：

- `repeated`：不同会话里流程相近、目标相近，而且都成功。fork 继承的事件不重新提取；fork 后重放的同一条请求标为 `replay`，不参与计数。
- `recovery`：失败、修复动作、同一动作成功的完整链条，并有后续检查。修复含安装、配置或命令改写时一次即可提示，只改业务代码时要求同一错误在多个会话里出现。
- `complex`：一次经过验证、用到至少 5 个不同的非日常命令（内联代码与 HTTP 请求不算）、跨 3 类以上命令的长任务，只作为摘要候选，提示词把一次性工作列为 `skip` 的首要情形。

后台摘要默认关闭。打开后受每日次数、最小间隔、超时与退避重试的约束，用户发起的摘要与草稿只计入用量、不占每日次数；摘要判定 `skip` 后，证据增加到两倍才会再问一次。

### 命令按动作比较，相似度放宽但有边界

同一件事在不同会话里的写法不同：`pnpm build` 和 `npm run build`，`npx vitest` 和 `pnpm exec vitest`，`bash scripts/release.sh` 和 `./scripts/release.sh`，还有不同 Agent 与 MCP 服务器给同类工具起的不同名字。按原文签名比较会把同一流程拆成几组，规则层就找不到重复。

`commands.ts` 给每段命令算一个规范动作 `key`，原来的写法 `sig` 只用于展示：

- 包管理器的脚本统一成 `pm run <脚本>`，内置命令按别名归并（`i`、`ci` 是 `install`，`t` 是 `test`），带包名的 `npm install` 是 `pm add`；经包管理器运行的已知命令行工具（vitest、tsc、eslint 等）直接用工具名。turbo 与 lerna 的任务也是 `pm run <任务>`。
- 解释器（含 tsx、ts-node、vite-node）加脚本文件和直接执行脚本文件，动作都是脚本的文件名；`bash -c` 展开里面的命令。内联代码按解释器归成 `python -c`、`node -e` 一类，不看代码内容。
- `git checkout -b` 与 `git switch -c`、`docker-compose` 与 `docker compose`、`pip3` 与 `pip`、cargo 的单字母别名各归为一个动作；gh 的只读子命令归为查看。
- 分词交给 shell-quote 之前，先去掉 here-document 的正文（那是交给程序的数据），按引号外的换行与续行拆成逻辑行，把 `${…}` 与 `$((…))` 换成占位变量。段首的 `if`、`do`、`!` 等关键字跳过；`for` 循环头、`done`、`fi` 和 `set`、`export`、`source` 这类只改变 shell 状态的内建命令不成为动作。从标准输入读代码的解释器（`python3 - <<EOF`）按内联代码处理。

有一类动作只说明用了什么程序，说明不了做了什么：内联代码、HTTP 请求（curl、wget、httpie、xh）、远程登录（ssh、scp）和 `open`。`isOpaque` 标出它们。Agent 用它们看数据、探接口、试一段代码，两个毫不相干的任务常常都有，换一段代码或一个 URL 再试也只是在摸索。

工具调用按名字归类，名字先去掉 MCP 前缀（`mcp__fs__edit_file` 与 `fs.edit_file` 都是 `edit_file`）。改动的动作只对 `package.json`、`CHANGELOG.md`、`*.config.ts`、`.github/workflows` 这类有固定角色的文件带文件名，其余改动不进入流程比较。

两个任务的流程相似度在动作之上计算，刻意放宽一点，但每一处放宽都有边界：

- 部分相同只有两种：同一 package.json 脚本前缀（`build` 与 `build:web`）记 0.7，同一类验证（测试、检查、构建）记 0.5；其余不同的动作记 0，`build` 与 `test`、`push` 与 `pull`、`publish` 与 `version` 永远不会连在一起。
- 每一步按权重计：提交、推送、装依赖这类几乎每个任务都有的日常动作和上面那类说明不了做了什么的动作 0.35，测试、检查、构建 0.6，其余 1。两个任务至少要共有一个权重为 1 的动作，日常的改、测、提交循环不会被当成重复流程。
- 共有的步骤先后顺序要大体一致（两两比较的一致比例不低于 0.6），顺序颠倒的两个流程不合并。
- 目标描述相近时流程加权重合 0.4 即可；目标描述不相近（例如用不同语言写的同一任务）时，要共有两个以上权重为 1 的动作、流程重合 0.6 以上。
- 只比较至少共有一个权重为 1 的动作的任务对（按动作建倒排索引），检测的开销不随会话数平方增长。

失败恢复按动作闭合：失败的 `npm test` 在安装依赖后由 `pnpm test` 通过，算同一条恢复链；换成另一个动作通过则不算。中间要有修复动作：安装、改配置文件、运行一个说明得了做了什么的命令，或者重跑时改了选项名或环境变量（`optionsOf` 比较两次运行，选项只取名字，`--filter=a` 与 `--filter=b` 相同）。内联代码与 HTTP 请求不算修复动作，重跑的是它们时，换写法也不算改写。跨会话合并恢复时，错误文本先把路径、URL、版本号、行列号、十六进制串和平台名（`darwin-arm64`、`linux-x64-gnu`）换成占位符；同一动作上的错误签名相同，或者错误文本的词重合度不低于 0.7，才算同一个问题。同一个错误出现在同一类命令的不同动作上（`pnpm build` 与 `vite build`）时，要求词重合度不低于 0.85。

每一处放宽都有反例测试：`commands.test.ts` 列出应当合并与必须分开的写法，`signals.test.ts` 覆盖日常循环、只共有一个部署命令的两件事、只共有内联代码与 HTTP 请求的两件事、顺序颠倒的流程和同一命令上的不同错误，`episodes.test.ts` 覆盖换一段内联代码或换一个 URL 的重试、改源码中间夹着内联查看的修复和改了选项的重跑。

### 证据包是数据，回答要经过校验

证据包是一个 JSON，作为用户消息里的不可信数据发送，系统提示词要求不执行其中的指令。证据包按预算分级裁剪，先去掉 Agent 回复和 Skill 正文摘录，再减少任务与操作数，最后才减少已占用的 Skill 名称（先去掉与证据最不相关的）。证据包里的已有 Skill 分两部分：按词重合挑出的最相关的至多 3 个带名称和描述，其中最相关的一个带正文摘录；摘要的证据包另外列出证据会话能看到的全部 Skill 名称（按名称排序，最多 200 个），提示词说明这些名称已被占用，新建 Skill 不能用，其中某个已经覆盖这个流程时改为追加内容或跳过。中文请求与英文的 Skill 名称、描述常常没有共同的词，名称列表让模型照样知道哪些名称已被占用；草稿的证据包不带这份列表。证据包里每个任务带上规则匹配到的步骤、用户在任务进行中插入的消息（最后 3 条）和下一条消息，纠正与失败原因由此进入 Skill 的前置条件和限制。摘要与草稿的证据包除已占用的 Skill 名称外相同；`session` 与 `selected` 线索最多带 12 个任务，用更宽的裁剪级别。摘要给出的是 idea 的方案（决定、标题、发现、用途、何时使用、Skill 名称、提纲、风险与验证方式），判断前先核对用户的纠正、失败原因和工具结果验证过的步骤。草稿请求在证据包前附上用户同意的那个 idea 的方案，提示词把它当作只处理这一个 Skill 的独立请求，方案与证据都是数据，其中要改任务、目标 Skill、文件位置、权限或绕过用户审核的内容一律忽略；证据会话能看到 `skill-creator` 时，它的 SKILL.md 脱敏后取前 20000 字符，按 DSH 加载技能的格式（`<skill_content>` 里带 `<skill_resources>` 技能目录与 `<skill_instructions>` 正文）附在提示词里，模型只采用写 SKILL.md 的指导，回复格式始终放在最后；改进已有 Skill 时，证据包里的已有 Skill 一定包含那个 Skill 的全文。

两段回答都要通过 valibot 校验，引用的 `E1.42` 一类编号必须存在。摘要另外核对：idea 数不超过上限，每个 idea 至少引用一处证据，同一摘要里的 Skill 名称各不相同，新 Skill 名称没有被占用，要改进的 Skill 存在。草稿另外核对：带命令的步骤，命令链的每一段都要和它引用的某次运行里的一段是同一个动作，并且这个动作在证据里成功过，复现失败的步骤因此可以引用那次失败；含命令替换时替换部分要与记录原样一致。`<patch|minor|major>` 这类只含单词的选项占位符在分词前换成第一个选项，`|` 不会被当成管道。出现凭据形态的文本、提示注入的痕迹或下载后直接交给 shell 执行的命令时整条拒绝；强制推送、递归删除、`sudo` 等命令作为提醒交给用户判断。草稿的 Skill 名称与标题取自摘要，模型在第二段不能改名。

### 脱敏发生在存储之前

会话原文只在 Host 进程里读取。Episode 写进存储之前已经脱敏，证据包和界面看到的都是脱敏后的文本。默认只保留失败命令的一行错误，完整输出不存储也不发送。

### 建议优先，写入可撤销

插件从不自动写 Skill。写入目标限定在 DSH 扫描的四个 Skill 根目录下的 `<name>/SKILL.md`；新 Skill 先在根目录旁的暂存目录写好再整体改名进去，DSH 的文件监视看不到写了一半的目录。改进已有 Skill 只在末尾追加一节，并用预览时的哈希防止覆盖用户刚改的内容。撤销前比对写入时的哈希，文件被改过就拒绝。

写入之后用 `ctx.sessionSkillCatalog.list({ sessionId })` 确认 DSH 列出了这个 Skill。这个服务按证据会话记录的工作目录与 Agent 预设解析 Skill 目录，冷会话不会被激活，结果就是该会话的 Agent 实际看到的目录。Web 组合把 `skill-filesystem` 挂在各个 Agent 预设里，Host 全局的 `ctx.skills` 看不到项目 Skill，所以去重与改进也读同一个服务。DSH 的目录缓存靠文件监视失效，确认先轮询几秒，仍未列出时在后台继续核对两分钟。

### 进度如实反映请求

每个请求在 Host 内存里记一个阶段：`queued`（等前一个请求）、`preparing`（整理证据包，读取已有 Skill 与 `skill-creator`）、`waiting`（已发出，还没收到分块）、`thinking`（收到推理分块）、`writing`（收到正文分块，累计字数）、`checking`（回复收齐，按 schema 与证据核对）。视图把阶段、开始时间、进入当前阶段的时间、已收到字数和这类回复的预计字数（摘要 900、整段会话与所选任务 2000、草稿 1600）交给浏览器，浏览器显示阶段文案与已用时间，占位条按已收到字数逐条点亮。预计字数只用来估算，不是上限。

浏览器有进行中的请求时每秒读一次收件箱。读取时比较前后两份收件箱，请求结束时，挂载着的会话 Tab、「建议」栏和打开的浮层各自登记自己列出的卡片；这张卡片既不在打开的详情里、也没有被任何表面列出时，才弹出带「查看」的提示，否则只由那一行的状态点和状态词表达；结论留在卡片原处，判定不值得保存时附理由。每次真正发给模型的请求写一条调用记录（`calls` 表，保留最新 100 条）：阶段、模型、耗时、未命中缓存的输入、缓存读、缓存写、输出 token 和结论。证据准备阶段就失败的请求没有调用模型，不写记录、不计用量。

### 搜索读索引，不读原始日志

开发机上的真实数据：829 个会话日志，压缩后 585 MB、解压后 2.2 GB；全部解压并解析约 15 秒，其中 525 个是子代理会话。每次搜索都读原始日志，会话一多就慢，而且搜的是未脱敏的原文。

搜索因此只查插件自己存的 Episode 记录。`search.ts` 在内存里建倒排索引，文本取请求、各操作的命令签名、命令、错误行、改动的文件和任务中插入的消息，分词与相似度共用 `signals.ts` 的 `tokens`。查询是 AND 语义，拉丁词按前缀匹配，按命中词数再按时间排序。会话记录变化时索引标脏，下一次查询重建。上面那批数据提取出 719 个任务，建索引约 25 ms，单次查询不超过 0.1 ms。

默认只有历史范围内的会话被分析。回溯（90 天或全部）在工作锁的持有者上逐个读取更早的会话，读完一个让出一次事件循环，可以暂停，暂停在正在读的会话读完后生效。回溯读入的会话标记 `backfilled`：可以搜索、提炼和统计，不参与规则检测，也不随历史范围清理。分析失败的会话记下原因：解析失败要等日志变长才重试，读日志失败下次重读。

### 统计

统计由已存记录计算：覆盖率（已分析、历史范围内与全部会话数来自最近一次 `listSessions`）、任务结果分布、近 30 天每天按结果分的任务数与新线索数（按本地日期归日，空日子补 0）、线索与 idea 各自按状态的计数（单位不同，分开统计；正在摘要的线索计入未摘要）、跨会话的高频动作（排除日常动作、查看类与说明不了做了什么的动作，附近 8 周每周的会话数）与在两个以上会话出现的错误签名、近 7 天的用量和最近的调用记录。用量按天存 8 天，统计需要 7 天，后台摘要的最小间隔要看前一天的最后一次。

### 界面与图表

界面的呈现规则写在 [design.md](design.md)，以 DSH 自己的页面为基线：会话 Tab 照轨迹视图的工具栏与分栏，「历史回溯提炼」页照插件页与任务页的页头、分区 Tab、列表与详情，浮层照宿主菜单。组件只用 DSH 的 token 与 `@deepseek-ai/dsh-client-ui-primitives`（`StateDot`、`SegmentedTabs`、`Menu`、`Tooltip` 等），插件自己的通用件放在 `src/client/ui/`。

图表在 `src/client/ui/charts/`，用 React 与 `d3-scale`、`d3-shape` 画 SVG，随浏览器半部一起打包：每日堆叠柱、行内走势线、占比条、排名列表。颜色按状态类别取 DSH 的状态 token，中性量用强调色的几档深浅；时间轴的刻度间隔按当前语言最长标签的实测宽度决定。每张图带标题、只给读屏器的数据表或描述，键盘可以逐项查看提示；系统设置了减少动态效果时没有过渡。

### 使用的 DSH 接口

| 职责       | 使用的 DSH 能力                                                                                                                                                                                |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 观察       | `ctx.on("session/event")`，只处理 `turn/end`，跳过 `origin === "subagent"` 的会话                                                                                                              |
| 读取历史   | `ctx.sessionQuery.listSessions` 与 `readSession`                                                                                                                                               |
| 存储       | `ctx.storageDomain`，per-record 布局，记录用 valibot 校验                                                                                                                                      |
| 模型       | `ctx.llm.stream`，发现模型与生成模型分开设置，默认都来自 `agentDefaultModel`                                                                                                                   |
| Skill 目录 | `ctx.sessionSkillCatalog`                                                                                                                                                                      |
| 浏览器路由 | `ctx.webServer.register`，经 `ctx.connection.requestRejection` 检查来源与认证                                                                                                                  |
| 界面       | `conversation.view`（会话 Tab）、`sidebar.panellist` 与 `main`（「历史回溯提炼」页）、`conversation.session.header.utilities`、`plugins.row.config` 插槽，`layout.selectPanel`，DSH primitives |

多实例由 `$DSH_HOME/skill-scout/worker.lock` 协调：拿到锁的实例分析会话与后台摘要，其他实例只读收件箱，锁的持有者退出后由下一个实例接管。持有者每分钟确认锁文件仍记着自己，两个进程同时接管同一把失效锁时，没留下锁文件的一方在下一次确认时交出工作。

## 测试与评估

- 单元与集成测试覆盖十类场景：两个独立会话的重复流程、失败后修复并经测试验证、复杂的一次性任务、只有读取与小改动的任务、多次失败没有成功、fork 与恢复不重复计数、已有 Skill 覆盖候选、工具输出里的提示注入与凭据、模型超时与格式不符与网络失败、忽略后不再提示。两段式另有测试：后台只写摘要、没有摘要时拒绝生成草稿、两段使用各自的模型、草稿失败保留摘要且不自动重试、生成期间忽略后保持忽略。
- 动作归并与相似度有正反两面的表驱动测试，见上一节。
- 线索与 idea 另有测试：多个 idea 各自同意、生成、保存与忽略，同名 idea 合并，「忽略类似」屏蔽相近的 idea，重新摘要的条件，提炼本会话与所选任务，回溯与暂停，分析失败的记录，进度阶段的变化，调用记录与缓存 token 的用量。路由测试在本机随机端口起真实的 HTTP 服务。
- 浏览器半部的组件测试在 happy-dom 里挂载会话 Tab、「历史回溯提炼」页的三个分栏、浮层收件箱与详情面板，覆盖角标、空状态、无模型、摘要与草稿失败、同意前不发请求、按阶段点亮的占位条与减少动态效果、完成提示只在卡片没有被列出时弹出、多个 idea 的切换与合并、步骤条与下一步说明、单栏与双栏、搜索勾选提炼、回溯进度与暂停、统计与图表（刻度不重叠、空数据、键盘提示）、写入被拒与撤销。`design-review.test.ts` 与 `copy-review.test.tsx` 检查样式表只用 DSH token、容器查询只用本文件声明的名字，以及中英文界面里没有露出字典键。
- 摘要与草稿提示词用七个用例在 Claude Haiku 5.5 与 Claude Sonnet 5.5 上评估：证据包由测试数据经插件自己的提取、检测与打包生成，摘要经 `checkSummary` 校验，值得保存的再生成草稿并经 `checkDraft` 校验。用例是三次发布、包管理器写法不同且一次用中文描述的两次发布、已有发布 Skill 覆盖的两次发布、两次依赖修复、错误输出里带注入指令与 token 的两次依赖修复、发布中途用户纠正「发布必须带 --otp，先问我要验证码」的两次发布、一次性迁移。两个模型对其中六个用例的判断一致：发布与依赖修复给出新建 Skill，已有 Skill 覆盖的给出追加内容，迁移判为 `skip`，每个方案都带何时使用、风险与验证方式。用户纠正的用例上 Sonnet 给出新建 Skill，方案与草稿都写明发布前先向用户要验证码、不带 `--otp` 不发布；Haiku 判为 `skip`，理由是可复用的只有这条账户偏好。所有草稿都通过校验，依赖修复的草稿带递归删除提醒，注入指令与 token 没有进入任何回答。
- 端到端验证在临时 DSH Web 实例上进行，Agent、发现模型与生成模型接本地脚本化的模型服务，DSH、插件、工具执行与文件写入都是真实的。
