`@agent-stash/dsh-skill-scout` is a DeepSeek Harness plugin. It reads finished sessions on your machine, judges whether a task succeeded only from tool results, and turns workflows that succeeded in several sessions, and fixes that passed a check after a failure, into Skill suggestions. A model first writes a short summary of what it found and which Skill it would create or extend. A draft is written only after you approve the summary, and nothing is saved until you have looked at the evidence and previewed the draft, and you can undo a write as long as the file has not changed since. The plugin needs DSH 0.2.1-rc.3 or later. The inbox and settings are in the DSH web interface and the desktop app.

## Usage

- Title bar icon: shows a count when new summaries or drafts arrive, and the count clears when you open the inbox. Without new suggestions it is only an icon, and the plugin shows no notifications. Set Header badge to Icon only to hide the count.
- Inbox: Needs your decision holds summaries waiting for your approval, drafts being written, and drafts ready to save; each card shows the purpose line from its summary. Found locally holds candidates that the rules found and that have no summary yet, including ones being summarized and ones whose summary failed. Saved, dismissed, and not-worth-saving suggestions move to History.
- Summary: before a summary exists, the Summary tab lists the steps the rules matched, and Summarize asks the discovery model for one. Afterwards it lists what was found, what the Skill is for, the Skill to create or add to, and an outline of its steps.
- Drafting: Draft Skill approves the summary, and the drafting model writes the Skill from it. While it writes, the Skill tab shows placeholder bars laid out like a SKILL.md; they stay still when the system asks for reduced motion.
- Other detail tabs: Skill is the draft, which you can edit, and Draft again writes it once more from the same summary. Changes shows the target path and the file diff. Evidence lists each source task's request, commands, exit codes, and one error line per failure, and Open session goes back to the session.
- Save: a new Skill goes to the project's `.agents/skills/<name>/SKILL.md` by default, or to `~/.agents/skills` for your user. When the summary finds that an existing Skill covers the task, the suggestion only appends a section to the end of that file.
- Undo, dismiss, and restore: you can undo a save. Dismiss moves a suggestion to History, and Dismiss similar also stops close variants from coming back. Dismissed suggestions can be restored.

## Rules

- Success comes only from tool results: after the last edit, the last run of every command succeeded. The agent saying it is done does not count, and neither does a task the user says is wrong in the next message.
- Commands are compared by action, so different spellings of one action count as one step: `pnpm build`, `npm run build`, and `yarn build`; `npx vitest` and `pnpm exec vitest`; `python -m pytest` and `pytest`; `bash scripts/release.sh` and `./scripts/release.sh`; `git checkout -b` and `git switch -c`; `turbo run build` and `pnpm build`; `npx tsx scripts/seed.ts` and `tsx scripts/seed.ts`. Different actions such as `pnpm build` and `pnpm test`, `git push` and `git pull`, or `npm publish` and `npm version` stay apart. Inline code (`python -c`, `node -e`), HTTP requests (`curl`, `wget`), remote logins (`ssh`), and `open` do not show what was done, so they carry as little weight as commits and pushes. Command and file-editing tools from other agents and MCP servers are classified by name.
- A repeated workflow must appear in at least 2 independent sessions (configurable), with similar steps that all succeeded. Steps that nearly every task has, such as commits, pushes, and dependency installs, carry little weight, so two tasks must share at least one other step. Scripts with the same prefix, such as `build` and `build:web`, count as partly the same, and the shared steps must run in roughly the same order. When the two requests are worded differently (for example one in Chinese and one in English), they must share at least two distinctive steps. History inherited by a fork counts once, and retries inside one session do not count as repeats.
- A recovery needs the whole chain: a command fails, then dependencies are installed, configuration changes, or the rerun changes its options or environment variables (`pnpm test --runInBand`), and then the same action succeeds, possibly spelled differently (`npm test` fails, `pnpm test` passes). Changing only files, arguments, or option values is not a fix, and neither is trying another inline snippet or another URL. A fix that only edits application code is suggested only when the same error shows up in several sessions; errors are compared after paths, version numbers, and platform names (`darwin-arm64`, `linux-x64-gnu`) become placeholders.
- A single long task that passed a check and used at least 5 distinct non-routine commands (not counting inline code and HTTP requests) from 3 or more command families also goes to the summary as a candidate, labeled Long verified task.
- The summary sees the most related existing Skill and can call the candidate a duplicate or propose an addition. After a summary says a candidate is not worth saving, it is summarized again only when the evidence doubles.

## Summaries and drafts

A model takes part in two steps, each with its own model setting. Without a chosen model, each step uses the agent's default model.

- The discovery model writes the summary: whether the candidate is worth saving and, if so, a title, what was found, what the Skill is for, a Skill name, and an outline of up to 8 steps. Background summaries are off by default; with them off, you can still click Summarize in a finding's detail. With them on, background summaries are limited by a daily count, a minimum interval, and a timeout. Requests you start yourself do not count toward the daily limit.
- The drafting model writes the draft only after you click Draft Skill. It writes only the Skill the summary names and follows its outline, and it turns your corrections during the task and the causes of failed commands into prerequisites, pitfalls, or limits. Drafts are never written in the background, and a failed draft is not retried automatically. A new summary discards the old draft.

The model receives redacted evidence: user requests, the working directory, command lines, paths of edited files, exit codes, one error line per failure (when Include error lines is on), the start of the agent's last reply, messages the user sent while the task ran (the last 3), the user's next message, the steps the rules matched, and the names and descriptions of up to 3 related existing Skills, with an excerpt of the most related SKILL.md. Full tool output, workspace file contents, and the agent's reasoning are not sent. When the evidence exceeds the character limit, the agent reply and the Skill excerpt are dropped first. A draft request also carries the summary you approved, and an addition to an existing Skill carries that Skill's full text. When the evidence session can see a Skill named `skill-creator`, a draft request also carries its SKILL.md (redacted, first 20,000 characters) as guidance for writing Skills; summary requests do not. Requests have no tools and run outside any session. Each answer must match the expected structure, and every cited piece of evidence must exist. A summary cannot propose a new Skill whose name is taken, or an addition to a Skill that does not exist. Every command in a draft step, including each part of a command chain, must be the same action as a run that the step cites, and that action must have succeeded somewhere in the evidence. A summary or draft that contains a credential, signs of prompt injection, a download piped into a shell, or a delete of the root or home directory is rejected. Commands such as sudo, force pushes, and recursive deletes are shown as cautions on the Skill tab.

## Data

- Session text is redacted on your machine before it is stored, sent, or shown: common API keys, tokens, private keys, auth headers, password assignments, credentials in URLs, and email addresses become placeholders, and home directories on macOS and Linux (`/Users/<name>`, `/home/<name>`) become `~`. You can add regular expressions in the settings.
- The plugin stores only episode records, suggestions (with their summaries and drafts), and model usage for the last two days (counts and tokens), in the DSH storage domain `skill_scout`. Records of sessions past the history range are deleted unless a pending suggestion cites them.
- The plugin does no analysis while the agent runs. It reads a session after a turn ends and the session stays idle for a while (2 minutes by default).
- When several DSH instances share one DSH home directory, only one of them analyzes sessions and writes background summaries.
- Writes happen only after you click Save, and only to `<name>/SKILL.md` under a project or user Skill directory. A new Skill is not written when a file already exists at the path. Adding to an existing Skill only appends a section to the end of the file, and nothing is written if the file changed after the preview.

## Install

<Tab value="Plugin market">
