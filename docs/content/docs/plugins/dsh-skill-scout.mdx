`@agent-stash/dsh-skill-scout` 是一个 DeepSeek Harness 插件。它在本机读取已经结束的会话，只根据工具结果判断任务是否成功，把在多个会话里重复成功的流程、失败后修复并通过检查的过程整理成 Skill 建议。模型先写几行摘要，说明发现了什么、打算新建或改进哪个 Skill；你同意摘要后才生成草稿，看过证据、预览过草稿才会写入。文件在保存后没有被改过时，可以撤销写入。插件需要 DSH 0.2.1-rc.3 或更新的版本，收件箱与设置页在 DSH 的 Web 界面和桌面版里提供。

## 使用

- 标题栏图标：出现新的摘要或草稿时显示数量，打开收件箱后清零。没有新建议时只有图标，插件不弹通知。设置里「标题栏角标」选「只显示图标」时不显示数量。
- 收件箱：「待你决定」是摘要等你同意、草稿正在生成或可以保存的建议，卡片上显示摘要里的用途说明。「本地发现」是规则找到、还没有摘要的候选，包括正在写摘要和摘要失败的。已保存、已忽略和判定不值得保存的建议收在「历史」里。
- 摘要：详情的「摘要」页在没有摘要时列出规则匹配到的步骤，点「生成摘要」请发现模型写摘要。有摘要后列出发现了什么、Skill 的用途、要新建或追加到的 Skill，以及步骤提纲。
- 生成草稿：点「生成 Skill 草稿」表示同意这份摘要，生成模型按摘要写出 Skill。生成期间「Skill」页显示按 SKILL.md 排版的占位条，系统设置了减少动态效果时占位条静止。
- 详情的其他页：「Skill」是可以直接修改的草稿，「重新生成」按同一份摘要再写一次；「改动」是目标路径和文件 diff；「证据」列出每个来源任务的请求、命令、退出码和失败时的一行错误，「打开会话」跳回原会话。
- 保存：新 Skill 默认写进项目的 `.agents/skills/<name>/SKILL.md`，也可以选用户级的 `~/.agents/skills`。摘要认为已有 Skill 覆盖了这个任务时，建议只在原文件末尾追加一节。
- 撤销、忽略与恢复：保存后可以撤销。「忽略」把建议移到历史，「忽略类似建议」让相近的流程以后也不再提示，忽略的建议可以恢复。

## 判断规则

- 成功只看工具结果：最后一次修改之后，每条命令的最后一次运行都成功。Agent 在回复里说完成了不算，用户下一条消息表示结果不对时也不算。
- 命令按动作比较，同一个动作的不同写法算同一步：`pnpm build`、`npm run build` 与 `yarn build`，`npx vitest` 与 `pnpm exec vitest`，`python -m pytest` 与 `pytest`，`bash scripts/release.sh` 与 `./scripts/release.sh`，`git checkout -b` 与 `git switch -c`，`turbo run build` 与 `pnpm build`，`npx tsx scripts/seed.ts` 与 `tsx scripts/seed.ts`。`pnpm build` 与 `pnpm test`、`git push` 与 `git pull`、`npm publish` 与 `npm version` 这类不同的动作不合并。内联代码（`python -c`、`node -e`）、HTTP 请求（`curl`、`wget`）、远程登录（`ssh`）和 `open` 从动作上看不出做了什么，在比较里和提交、推送一样权重低。其他 Agent 与 MCP 服务器的执行命令、改文件类工具按名字归类。
- 重复流程要出现在至少 2 个独立会话里（可调），流程相近并且都成功。提交、推送、安装依赖这类每个任务都有的步骤权重低，两个任务至少要共有一个其他步骤；`build` 与 `build:web` 这类同前缀的脚本算部分相同；共有步骤的先后顺序要大体一致。请求描述不相近（例如一个用中文、一个用英文）时，要共有两个以上有区分度的步骤。从别的会话 fork 出来的历史不重复计数，同一会话里的反复重试不算重复。
- 失败恢复要有完整的链条：命令失败，接着安装依赖、改配置，或者重跑时改了选项或环境变量（`pnpm test --runInBand`），然后同一个动作成功，写法可以不同（`npm test` 失败后 `pnpm test` 通过）。只换文件、参数或选项的值不算修复，换一段内联代码或换一个 URL 也不算。只改业务代码的修复，要在多个会话里遇到同一个错误才提示；比较错误时，路径、版本号和平台名（`darwin-arm64`、`linux-x64-gnu`）先换成占位符。
- 通过检查、用到至少 5 个不同的非日常命令（内联代码与 HTTP 请求不算）且跨 3 类以上命令的单个长任务，也会作为候选交给摘要，卡片上标为「经验证的长任务」。
- 写摘要时附上最相关的已有 Skill，模型可以判为重复，或者建议追加内容。摘要判定不值得保存后，证据增加到两倍才重新摘要。

## 摘要与草稿

/>

模型分两步参与，两步的模型分开设置，不选时都跟随 Agent 的默认模型：

- 摘要由发现模型写：判断值不值得保存，值得时给出标题、发现了什么、Skill 的用途、Skill 名称和最多 8 条步骤提纲。后台摘要默认关闭，关闭时也可以在详情里点「生成摘要」。打开后，后台摘要受每日次数、最小间隔和超时限制，手动发起的请求不计入每日次数。
- 草稿由生成模型写：只在你点「生成 Skill 草稿」之后请求，只写摘要指定的那个 Skill，按摘要的提纲写；你在任务中的纠正和命令失败的原因写成前置条件、注意事项或限制。后台从不生成草稿，失败也不自动重试。重新生成摘要会让旧草稿失效。

发给模型的是脱敏后的证据：用户请求、工作目录、命令行、改动过的文件路径、退出码、每次失败的一行错误（「包含错误行」打开时）、Agent 最后一条回复的开头、任务进行中用户插入的消息（最后 3 条）、用户的下一条消息、规则匹配到的步骤，以及最多 3 个相关的已有 Skill 的名称和描述，其中最相关的一个附带 SKILL.md 正文摘录。完整的工具输出、工作区文件内容和 Agent 的思考过程不发送。证据超出字符上限时，先去掉 Agent 回复和 Skill 正文摘录。草稿请求另外带上你同意的摘要，追加内容时附上要改进的 Skill 全文。证据会话能看到名为 `skill-creator` 的 Skill 时，草稿请求还带上它的 SKILL.md（脱敏后取前 20000 字符）作为写 Skill 的指南，摘要请求不带。请求不带工具，也不在任何会话里运行。模型的回答要符合约定的结构，引用的证据都要存在。摘要里的新 Skill 名称不能和已有 Skill 重名，要改进的 Skill 必须存在。草稿里带命令的步骤，每一段命令都要和它引用的某次运行是同一个动作，而且这个动作在证据里成功过。含凭据、提示注入痕迹、下载后直接执行或删除根目录与主目录的摘要和草稿整条拒绝，sudo、强制推送、递归删除这类命令作为提醒显示在「Skill」页。

## 数据

- 会话文本在存储、发送和显示之前先在本机脱敏：常见的 API Key、token、私钥、认证头、密码赋值、URL 里的账号密码和邮箱都换成占位符，macOS 与 Linux 的用户主目录（`/Users/<name>`、`/home/<name>`）换成 `~`。设置里可以追加正则规则。
- 插件只存 Episode 记录、建议（含摘要与草稿）和最近两天的模型用量（次数与 token 数），放在 DSH storage domain `skill_scout` 里。超出历史范围的会话记录会被删除，仍待处理的建议引用的除外。
- Agent 运行时插件不做分析：回合结束并空闲一段时间（默认 2 分钟）后才读取这个会话。
- 多个 DSH 实例共用同一个 DSH 目录时，只有一个实例在后台分析会话和写摘要。
- 写入只发生在你点保存之后，目标只能是项目或用户 Skill 目录下的 `<name>/SKILL.md`。新建时目标已有文件就不写入。追加到已有 Skill 时只在末尾加一节，预览之后文件被改过就不写入。
